# Changelog

## 1.4.0 - 2026-11-18

Fixed (1.4.0-beta.10): Show when re-checks are no longer folded together. The SDK kept one shared re-check event: two re-checks close together went out as ONE placements request for both keys carrying only the last event (`track('ev_a'); track('ev_b')` sent `{ placements: ['xk_a', 'xk_b'], recheckEvent: ev_b }`), and re-checks waiting for a failed delivery joined each other's request when it came back (25 waiting re-checks for one key sent 2 requests). Each re-check is now a request of its own for its keys and its event, as on iOS and Android: an event never rides on another key's re-check, and a re-check never joins a normal placements fetch. The waiting rules are unchanged - at most 20 (the oldest dropped), 60 s, tied to the visitor, consent and page.

Fixed (1.4.0-beta.10): the on-site editor (`joryio-editor.min.js`) could throw `Failed to execute 'remove' on 'Element'` into the customer's page when a variable's fallback popover closed. Closing it removed it, the removal moved focus, and the popover's own focusout handler removed it a second time mid-removal. The popover is now forgotten before it is removed and its removal never throws; the New text field's blur handlers likewise ignore a field that is being redrawn (a redraw while the field had focus could draw it twice). Editor bundle 19227 bytes gzip (budget 19500).

Fixed (1.4.0-beta.10): feature flags - `/v1/flags/evaluate` and `/v1/flags/exposures` sent `attributes: {}` on the web, so a flag rule on an attribute never matched a website visitor. They now carry the attributes set on this device in this session (`setAttributes` / `setAttribute`, and `push_permission` where the site uses web push) - the same keys and values iOS and Android send. The browser has no app version, so `context` carries `url` where the apps carry `appVersion`, as before.

Added (1.4.0-beta.9): Show when (BACKLOG D465) - the moment a Placement or Web personalization campaign's content is revealed in a page view. The SDK fetches the content as before, holds it, and reveals it at its moment: `showWhen: { kind: 'load' }` (the default; also: no field), `{ kind: 'seconds', seconds: 1..3600 }` (visible seconds on the page - hidden-tab time does not count, the `time_on_page` trigger's clock), `{ kind: 'scroll', percent: 1..100 }` (share of the page scrolled, like `scroll_depth`), `{ kind: 'exit' }` (the pointer leaves the window through the top, like `exit_intent`; on a touch device a fast scroll up - see the touch exit intent entry below) and `{ kind: 'event', event: '<name>' }` (that event was tracked in this visit - the SDK session, any properties, before or after the content arrived; the names are kept in memory and sessionStorage per session id). New exports `SHOW_WHEN_KINDS` (`['load', 'seconds', 'scroll', 'exit', 'event']`) and the types `ShowWhen`, `ShowWhenKind`. Placements: an item with `items[].showWhen` other than load is neither drawn nor handed to `getPlacements` / `onPlacementsUpdated` until its moment; then the key's spots re-draw and `onPlacementsUpdated` fires, and the impression (`in_app.displayed`) is reported only once it is shown and viewable. Once revealed it stays for the page view; a route change (SPA) holds it again until the new page's moment. A control answer's `showWhen` delays `control_viewed` until that moment AND the spot is viewable (a `Placement.markDisplayed()` before the moment is ignored, and `onPlacementsUpdated` fires at the moment so the app calls it again); `deferredControls: [{ controlToken, showWhen }]` on a filled answer are each reported once, as today's control report, when their own moment has come (`load` = at once) and the spot was viewable in this page view (a drawn item or the control spot viewable, or any `markDisplayed()` of that placement). Page edits: an experience with `experiences[].showWhen` other than load is not applied until its moment, its selectors are never in the anti-flicker rule nor remembered for it (the original shows until then), `in_app.displayed` is reported when an edit lands after the moment, and a control experience's `control_viewed` waits for the moment as well as for a selector on the page; a server-applied edit (`#joryio-server-page-edits`) of an experience that now waits for a moment is undone and applied by the SDK at the moment. Re-check: when an event named in an answer's `recheckOn` (placements per key, page edits for the page) or one held content waits on is tracked, the SDK asks again at once - the placement key past the 30 s client limit, and the page edits for the current page - at most once per (key or page, event) per page view, and never before the event itself reached the server: it waits for a flush already running, flushes the queue, and asks only once the event has left the queue (delivered); a failed flush keeps the re-check waiting, and it runs once, after the next flush that delivers the event. The re-check request (only that one) carries the event as `recheckEvent: { name, eventId, properties }` - the queued event's client `eventId` and its properties as queued - which the server counts as arrived in the audience conditions (only for an event name a live Show when campaign waits on), so its own write of the event cannot race the answer. A waiting re-check is tied to the visitor, consent and page it was queued for: it is dropped on identify to another user, reset / resetTo / wipeData, opt-out or a consent change, a route change and destroy, and when it is older than 60 s; at most 20 wait (the oldest dropped). So one person's event never rides on another person's request. An unknown kind or an invalid value is never shown (never treated as load). No capability: placements and page edits exist only in 1.4.0 betas, so Joryio serves Show when campaigns to every build, and a beta before 1.4.0-beta.9 shows such content at once, on load. Changed (1.4.0-beta.9): the `page_edit_device` capability and the `PAGE_EDIT_DEVICE_CAPABILITY` export are removed - the server now sends per-device edits to every build (1.4.0-beta.8 applies them per device as before; a build before beta.8 applies them on every device). The legacy item `triggers` event window is unchanged. `joryio.min.js` 72610 bytes gzip (274845 raw), before 70487 gzip (266695 raw); budget raised from 71000 to 72800. Parity: iOS, Android: placements load/seconds/event (scroll and exit need a page; the server never sends them to an app); React Native/Unity inherit from the native SDKs; Web personalization web only.

Fixed (1.4.0-beta.9): exit intent on phones and tablets. Show when `{ kind: 'exit' }` and the **Exit intent** page trigger of in-app messages on a website (`exit_intent`) waited for the mouse to leave the window through the top, so on a touch device they never fired and the content was never shown. On a device whose primary input is touch - `matchMedia('(hover: none) and (pointer: coarse)')`, read live; a touch-screen laptop or a tablet with a trackpad reports a fine pointer with hover and keeps the desktop rule - exit intent is now a fast scroll up after reading down the page, the gesture of someone heading for the address bar or the tab switcher: once the visitor has scrolled down at least 25% of the page or 400 px in this page view, a scroll up of at least 120 px within 300 ms fires it, never in the first 3 s of the page view (load or route change), so a restored scroll position or an anchor jump does not count. Once per page view, like the desktop rule (one flag, reset by a route change); the scroll positions are sampled at most every 50 ms on the existing passive scroll listener, which `destroy()` removes. Desktop is unchanged. No `visibilitychange` trigger is added. New export `TOUCH_EXIT_INTENT` (the thresholds). `joryio.min.js` 74023 bytes gzip (280073 raw), under the 74300 budget. Parity: iOS, Android, React Native and Unity are not applicable - `exit` (like `scroll`) needs a page; the server never serves it to a request without page context (`showWhenServable`, `SHOW_WHEN_WEB_ONLY_KINDS`), the dashboard disables it for an apps-only placement, and the native SDKs parse a stray `exit` as never shown, the same on all four.

Added (1.4.0-beta.9): server-filled placement slots (D466). The Joryio store plugins (WooCommerce / WordPress 1.6.48, Magento 1.4.36, PrestaShop 1.2.30) may write a placement slot's content into the page's HTML when Joryio's answer for that slot is the same for every visitor (audience everyone, one treatment and no Control Group, no Liquid, nothing per person, Show when "Page loads"). They mark it: `data-joryio-server-filled="<placementKey>:<campaignId>:<variantId>"` on the slot element (a `data-joryio-placement` element of the theme, or one a page edit inserted), the drawing in a `.joryio-placement` wrapper with `data-joryio-server-fill` (the same token) - HTML content in a declarative shadow root, product cards with the SDK's classes - and the marker block `#joryio-server-page-edits` lists the fills (`fills: [{ placementKey, campaignId, variantId, products }]`). The SDK trusts a fill only when the slot, the wrapper and the marker block (a JSON `<script>` directly in `<head>`, as for server page edits) agree. When the visitor's own answer is the same campaign, variant and products, it keeps the drawing - no redraw, no frame - reports its impression with the visitor's own delivery token once it is viewable (nothing without consent, as for every item) and reports clicks with the SDK's own names (`product:<id>` for a product card, the frame's `link_click` / `cta_click` in HTML content), opening links through the link handler in a new tab. When the answer differs (another campaign or variant, other products, nothing - suppressed, paused, capped - or a control), the drawing is removed and the slot drawn from the visitor's answer, or collapsed per its empty behaviour. Before the answer (or when the request fails) the drawing stays as sent. A fill that does not check out, or an HTML fill in an SDK with `allowHtmlJsInAppMessages` off, is removed at once. A browser without declarative shadow DOM leaves the template inert; the SDK attaches it. No new options or exports; a page without the marker behaves exactly as before. `joryio.min.js` 73714 bytes gzip (278898 raw), before 72610; budget raised from 72800 to 74300. Web only: iOS, Android, React Native and Unity are not applicable - a store plugin fills a slot in server-rendered HTML, a web concept.

Added (1.4.0-beta.8): page edits per device, and a Desktop / Mobile toggle in the on-site editor. An edit may carry `device: 'mobile' | 'desktop'` (absent or `'all'` = every device, so every existing edit is unchanged). The SDK applies an edit only on its device and, when the viewport crosses the breakpoint (a resized window, a turned phone), undoes every edit and applies the ones for the new width again, so a desktop and a mobile version of one element never fight; the exposure is still reported once, when an edit of the visitor's variant first lands. An edit with a device this build does not know is skipped, never applied everywhere. The page-edits request sends the new capability `page_edit_device` (`PAGE_EDIT_DEVICE_CAPABILITY`): Joryio sends per-device edits only to an SDK that sends it, so 1.4.0-beta.7 and earlier get the edits for all devices only and never apply a mobile version on a desktop. The editor (`joryio-editor.min.js`): a Desktop / Mobile toggle in the dock; Mobile shows the page at phone width (390 px) in a same-origin frame of the current address with `?joryio_editor=frame`, and the editor works on the frame's document (hover, selection, the live preview, selectors) while its own UI stays in the tab. New editor words `view`, `viewDesktop`, `viewMobile`, `appliesTo`, `devAll`, `devMobile`, `devDesktop`, `deviceHidden`, `frameBlocked`. `joryio.min.js` 70487 bytes gzip (budget raised from 70500 to 71000); `joryio-editor.min.js` 19184 gzip with the fixes below (budget raised from 17000 to 19500, loaded only in a tab the dashboard opened for the editor). Fixed (1.4.0-beta.6): a beta reports its own version. Added (1.4.0-beta.6): page-edit position `replace` - "Instead of it" (Joryio BACKLOG D444, from main, PR #876). An `insert_placement` edit at `replace` hides the chosen element (`display: none !important`, as `hide` does) and puts the placement spot right after it, so the placement takes the element's place; undoing it (destroy, a route change, an answer that no longer carries it) removes the spot and shows the element as it was. A store plugin may write it into the page's HTML too (server-side page edits, D450): the SDK keeps it when the answer carries it, and undoes both parts - the spot, and the hide with the same rule as a server-written `hide` - when it does not. Changed (1.4.0-beta.5): one subscription type for every listener, the same on all five SDKs (Joryio BACKLOG D444 / D446, owner decisions 2026-11-23). `onCardsUpdated`, `onPlacementsUpdated` and `onFlagsUpdated` return a `JoryioSubscription` (new exported type): `cancel()` stops the updates - the same type name and method on iOS, Android, React Native and Unity (`JoryioSubscription.Cancel()`). It can still be called, `sub()` being `sub.cancel()`, so code that called the returned function keeps working. Cancelling twice is harmless, and the same callback subscribed twice now counts as two subscriptions. Neither placements, flags nor cards are in a final release (none of the three listeners exists in 1.3.3), so the breaking renames are made now. No wire changes.

Changed (1.4.0-beta.4): the page-edit site settings (`GET /v1/in-app/site-settings`) are asked once per SDK session instead of once per page load. The answer is kept in `sessionStorage`, per workspace (`jry_page_edit_site_<hash>`, the SDK-key hash of the other page-edit stores), tied to the session id - a new session asks again - and refreshed at most every `SITE_SETTINGS_SESSION_REFRESH_SECONDS` (600, new export) within the session; the server's `ttlSeconds` (60, the browser and CDN cache lifetime) no longer shortens that. With a stored answer a page no longer waits for the site settings before asking for its edits: the stored answer is used at once and refreshed in the background when it is 10 minutes old (if that refresh finds a newly live campaign, the page asks for its edits then). What this means for marketers: a page-edit campaign launched while a visitor is on the site reaches that visitor within 10 minutes (on a new session at once); pausing is not delayed, because `/v1/in-app/page-edits` checks every campaign's liveness on every page. A failed request is still "unknown": nothing is stored, the page asks `/v1/in-app/page-edits` as before, and a failed background refresh drops the stale answer. `reset()`, `resetTo()`, `wipeData()` and every consent change remove the stored answer, as the other per-workspace stores; `identify()` keeps it - it is the same for every visitor. No wire changes. Web only: iOS, Android, React Native and Unity are not applicable - page edits are a browser concept (no DOM, no page loads in an app screen).

Web only: iOS, Android, React Native and Unity are not applicable - nothing is loaded at run time on those platforms.

Added: server-side page edits (Joryio BACKLOG D450, not released yet). The Joryio store plugins (WooCommerce / WordPress 1.6.45, Magento 1.4.33, PrestaShop 1.2.27) write the page edits that are the same for every visitor into the page's HTML and mark them: a JSON block `<script type="application/json" id="joryio-server-page-edits">` listing the edits applied, and `data-joryio-applied="<campaignId>:<editId>"` (with undo data in `data-joryio-orig`) on each changed element. The SDK never applies a marked edit again (same campaign, variant and edit), counts it as landed for the one exposure report, never holds a marked element back in the anti-flicker rule, and undoes a marked edit when the visitor's definitive answer no longer carries it (paused or changed campaign, a suppressed visitor, a control, page edits switched off for the site) or after a route change to another page. The marker is trusted only as a JSON `<script>` directly in `<head>` (an element with that id elsewhere - user content, DOM clobbering - is ignored), and an undo writes back only to an element that still shows exactly the value the server applied, only addresses that are http(s) or relative (anything else removes the attribute), never a style string from the marker (it removes the one declaration the server added), and a replaced text comes back rebuilt node by node through an allowlist of inline text elements and attributes (no script, frame, object, embed, meta, base, link, style, form, svg or math element, no on*, style, srcdoc or data attribute, URLs checked as above) - the kept markup is never made live as is. ## 1.3.3 - 2026-11-03

Fixed: an in-app message counts as displayed only once someone could have seen it. It used to be counted - `in_app.displayed` reported and the campaign's frequency cap spent - the moment it was put on the page, so a message that appeared during a sign-in redirect, or just as someone clicked a logout link, used up the cap while it was visible for a flash at most. Now:

- a message appears only once the page has finished loading and gone idle, and never while the page is unloading (`beforeunload` / `pagehide`);
- it counts as displayed after it has been on screen for `IN_APP_DISPLAY_DWELL_MS` (1000 ms) with the tab visible. If the tab is hidden first the timer starts again when it is visible; if the page unloads first, nothing is reported, the frequency cap is untouched, and the message is eligible again on the next page;
- a click or a close by the person before then counts as seen: `displayed` is reported first, then the click or dismissal. Removal by the SDK or by your code (`dismissInAppMessage`, `reset()`) before then reports nothing.

Changed: `inApp.displayOptions.onDisplay` fires when the message counts as displayed, together with the `displayed` report, rather than when it is put on screen - the same timing as `onMessageDisplay` on iOS. `IN_APP_DISPLAY_DWELL_MS` is exported. No wire changes.

Fixed: the script-tag file (`joryio.min.js`, `joryio.umd.js`) is safe on a page with an AMD loader such as RequireJS (every Magento Luma store). Loaded by a plain `<script>`, the old UMD wrapper called an anonymous `define()`, which RequireJS attached to another module that was loading or reported as "Mismatched anonymous define() module" - and the SDK did not start. The SDK now always starts and sets `window.Joryio`; on an AMD page it defines an anonymous module only when RequireJS itself requested the file, and otherwise the named module `joryio-web-sdk`. Loading it with `require()` under any module id, as a CommonJS module or from npm (`import` / `require`) is unchanged.
