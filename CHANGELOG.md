# Changelog

## 1.4.0 - 2026-11-18

Changed (1.4.0-beta.6): the on-site Web personalization editor (`joryio-editor.min.js`) is redesigned (Joryio BACKLOG D444, design handoff screens 1-3). All of its UI is in one closed shadow root on an `all: initial` host, so the site's CSS cannot restyle it and its CSS cannot reach the site; the previews it puts in the page are custom elements with their own shadow roots (never a `div`, so the site's `:nth-of-type` selectors do not move). Hover shows a dashed outline with a label ("Heading · h1"); a click selects (it never reaches the site); arrow up / down, two buttons and a breadcrumb ("Page › Main › Heading") move to the element around it or the first one inside it. A light side panel names the element and how many elements its selector matches (1 match / "Matches N - all will change" / Not found) and offers Change text, Change link (off with "Not a link"), Change image (images only, `replace_image`), Hide it and Add content slot (`insert_placement`, Above it / Below it / Instead of it = position `replace` / inside at the start or end), each with its own field: the new text with "Was:", Insert chips for profile fields (`{{ user.firstName }}`, the dashboard's format) and "If a value is missing" (the `| default:`); the address; the slot name, turned into a placement key as typed ("after blog" -> `after_blog`, never refused). A collapsible CSS selector field for developers. Every edit shows live on the page while editing, with the dashboard's sample values for the variables, else their fallbacks; text is set as text, addresses must be http(s), and the original nodes come back on cancel, undo and stop. A dock shows campaign, variant and page, "N edits" (a click jumps to that edit), Undo and "Save & return to Joryio" (Esc still finishes). New messages with the dashboard, all origin- and window-checked: `joryio:editor-context` (dashboard -> editor: campaign and variant names, the variant's edits, profile fields, placements, sample values, translated words and `dir`), `joryio:editor-focus` `{ id }` (jump to an edit), `joryio:editor-remove` `{ id }` (Undo of a new edit) and `joryio:editor-done`; `joryio:editor-pick` now carries the edit's `id` (an id the dashboard has replaces that edit). A dashboard that sends no context works as before, with Undo off. The editor's words are English unless the dashboard sends its translations. `joryio-editor.min.js` 13127 bytes gzip, budget raised from 3500 to 14000 (loaded only in a tab the dashboard opened for the editor; no visitor downloads it). Web only: iOS, Android, React Native and Unity are not applicable - the editor edits a web page in a browser tab.

Fixed (1.4.0-beta.6): a beta reports its own version. The release build writes the beta (`1.4.0-beta.6`) into `SDK_VERSION` of the published copy, not only into `package.json`: the beta sends it in `X-Joryio-SDK-Version`, and its side files (`joryio-cards-ui.min.js`, `joryio-editor.min.js`) are loaded from `sdk.joryio.com/web/1.4.0-beta.6/`. Before, a beta said `1.4.0`, so an npm beta (bundled into the site, or loaded from a CDN that is not sdk.joryio.com) asked `web/1.4.0/` and `web/1/` - neither exists for a beta - and the card feed showed `unavailable`. A pre-release never falls back to the major channel `web/<major>/` (it holds finals only); a final keeps it as the last resort. The source keeps saying `1.4.0`. The same fix on iOS, Android, React Native and Unity.

Added (1.4.0-beta.6): page-edit position `replace` - "Instead of it" (Joryio BACKLOG D444, from main, PR #876). An `insert_placement` edit at `replace` hides the chosen element (`display: none !important`, as `hide` does) and puts the placement spot right after it, so the placement takes the element's place; undoing it (destroy, a route change, an answer that no longer carries it) removes the spot and shows the element as it was. A store plugin may write it into the page's HTML too (server-side page edits, D450): the SDK keeps it when the answer carries it, and undoes both parts - the spot, and the hide with the same rule as a server-written `hide` - when it does not. A build before this one reads `replace` as `after` (the element stays visible, the spot goes after it). Web only: iOS, Android, React Native and Unity are not applicable - page edits change a web page's DOM.

Changed (1.4.0-beta.5): one subscription type for every listener, the same on all five SDKs (Joryio BACKLOG D444 / D446, owner decisions 2026-11-23). `onCardsUpdated`, `onPlacementsUpdated` and `onFlagsUpdated` return a `JoryioSubscription` (new exported type): `cancel()` stops the updates - the same type name and method on iOS, Android, React Native and Unity (`JoryioSubscription.Cancel()`). It can still be called, `sub()` being `sub.cancel()`, so code that called the returned function keeps working. Cancelling twice is harmless, and the same callback subscribed twice now counts as two subscriptions. Neither placements, flags nor cards are in a final release (none of the three listeners exists in 1.3.3), so the breaking renames are made now. No wire changes.

Changed (1.4.0-beta.4): the page-edit site settings (`GET /v1/in-app/site-settings`) are asked once per SDK session instead of once per page load. The answer is kept in `sessionStorage`, per workspace (`jry_page_edit_site_<hash>`, the SDK-key hash of the other page-edit stores), tied to the session id - a new session asks again - and refreshed at most every `SITE_SETTINGS_SESSION_REFRESH_SECONDS` (600, new export) within the session; the server's `ttlSeconds` (60, the browser and CDN cache lifetime) no longer shortens that. With a stored answer a page no longer waits for the site settings before asking for its edits: the stored answer is used at once and refreshed in the background when it is 10 minutes old (if that refresh finds a newly live campaign, the page asks for its edits then). What this means for marketers: a page-edit campaign launched while a visitor is on the site reaches that visitor within 10 minutes (on a new session at once); pausing is not delayed, because `/v1/in-app/page-edits` checks every campaign's liveness on every page. A failed request is still "unknown": nothing is stored, the page asks `/v1/in-app/page-edits` as before, and a failed background refresh drops the stale answer. `reset()`, `resetTo()`, `wipeData()` and every consent change remove the stored answer, as the other per-workspace stores; `identify()` keeps it - it is the same for every visitor. No wire changes. Web only: iOS, Android, React Native and Unity are not applicable - page edits are a browser concept (no DOM, no page loads in an app screen).

Fixed (1.4.0-beta.4): the lazily loaded files (`joryio-editor.min.js`, `joryio-cards-ui.min.js`) are loaded from the folder `joryio.min.js` itself was loaded from first (read from its script tag; https only, file name `joryio.min.js`), then from `sdk.joryio.com/web/<version>/` and `/web/<major>/` as before. Before, a beta (whose `SDK_VERSION` says the final version) loaded from `sdk.joryio.com/web/1.4.0-beta.4/` or from the npm package's `dist/` on a CDN asked `web/1.4.0/` (not published yet) and then `web/1/` - the previous final's editor and card feed. A core loaded from the major channel `web/<major>/` keeps the exact version first (the channel moves); an SDK bundled into the site's own code is unchanged; `editorScriptUrl` / `cardsUiScriptUrl` still replace all of it. `joryio.min.js` 69961 bytes gzip, budget raised to 70500. Web only: iOS, Android, React Native and Unity are not applicable - nothing is loaded at run time on those platforms.

Added: server-side page edits (Joryio BACKLOG D450, not released yet). The Joryio store plugins (WooCommerce / WordPress 1.6.45, Magento 1.4.33, PrestaShop 1.2.27) write the page edits that are the same for every visitor into the page's HTML and mark them: a JSON block `<script type="application/json" id="joryio-server-page-edits">` listing the edits applied, and `data-joryio-applied="<campaignId>:<editId>"` (with undo data in `data-joryio-orig`) on each changed element. The SDK never applies a marked edit again (same campaign, variant and edit), counts it as landed for the one exposure report, never holds a marked element back in the anti-flicker rule, and undoes a marked edit when the visitor's definitive answer no longer carries it (paused or changed campaign, a suppressed visitor, a control, page edits switched off for the site) or after a route change to another page. The marker is trusted only as a JSON `<script>` directly in `<head>` (an element with that id elsewhere - user content, DOM clobbering - is ignored), and an undo writes back only to an element that still shows exactly the value the server applied, only addresses that are http(s) or relative (anything else removes the attribute), never a style string from the marker (it removes the one declaration the server added), and a replaced text comes back rebuilt node by node through an allowlist of inline text elements and attributes (no script, frame, object, embed, meta, base, link, style, form, svg or math element, no on*, style, srcdoc or data attribute, URLs checked as above) - the kept markup is never made live as is. A failed answer keeps the page as sent. `joryio.min.js` 68943 bytes gzip, budget raised to 69300. No new options; a page without the marker behaves exactly as before. Web only: iOS, Android, React Native and Unity are not applicable - server-rendered HTML is a browser concept.

Added: the default placement view draws an item's recommended products (Joryio BACKLOG D444) - a horizontal row of product cards (image, title, price with the compare-at price struck through, optional button) below the item's content, or alone for a data item. A tap reports `clicked` with elementId `product:<id>` and opens the product link like a `deep_link` button, through `setLinkHandler` first (source `placement`). `insertPlacement` options `showProducts` (default true), `productButtonText`, `productCardWidth`; CSS classes `joryio-placement-product*`. New exports `PLACEMENT_PRODUCT_ELEMENT_PREFIX`, `PLACEMENT_PRODUCT_CARD_WIDTH`, `placementProductElementId`. A data item with products was not drawn before; `showProducts: false` keeps that.

Changed: the default card feed's drawing code (`mountCardFeed`) is its own file, `joryio-cards-ui.min.js`, next to `joryio.min.js` on the SDK host (`sdk.joryio.com/web/<version>/`, then `/web/<major>/`) and in the npm package's `dist/` (Joryio BACKLOG D444, not released yet), so a visitor of a page without a feed never downloads it: `joryio.min.js` 68077 -> 67289 bytes gzip, the new file 2242 gzip; the size budget is lowered to 68300. The card data API (`getCards`, `getUnreadCardCount`, `markCard*`, `dismissCard`, `refreshCards`, `onCardsUpdated`) stays in the core. `mountCardFeed(element, options)` keeps its signature and still returns its handle at once; the feed is drawn as soon as the file has loaded (at once when it already is, such as for a second feed), and `remove()` before that draws nothing. If the file cannot be loaded - a Content-Security-Policy whose `script-src` does not allow `https://sdk.joryio.com`, a network failure - the SDK logs a warning, sets `data-joryio-card-feed-state="unavailable"` on the element and throws nothing; the data API keeps working and the next `mountCardFeed` tries again. New init option `cardsUiScriptUrl` for a self-hosted SDK; a bundler can `import '@joryio/web-sdk/dist/joryio-cards-ui.min.js'` once to skip the fetch. The renderer gets only what the public card API already offers (the feed view, the reports, the link handler, the next page), through the core's handle - never the delivery tokens or the storage. No wire changes. Web only: iOS, Android, React Native and Unity are not applicable - their feed views are compiled into the app binary, which is not downloaded per page view, so there is nothing to split (React Native's `<JoryioCardFeed />` and Unity wrap those native SDKs).

Changed: the point-and-click page editor is its own file, `joryio-editor.min.js`, next to `joryio.min.js` on the SDK host (`sdk.joryio.com/web/<version>/`, then `/web/<major>/`) and in the npm package's `dist/` (Joryio BACKLOG D444, not released yet). The core keeps only the handshake: the file is loaded only in a tab the Joryio dashboard opened with `?joryio_editor=1`, and only after Joryio accepted the editor token - no visitor downloads it. `joryio.min.js` is 238,080 bytes (63,464 gzip), down from 240,133 (64,424 gzip); the editor file is 7,565 bytes (3,111 gzip). A site with a Content-Security-Policy needs `script-src https://sdk.joryio.com` for the editor (as for the SDK itself). New init option `editorScriptUrl` for a self-hosted SDK.

Added: `pageEdits: false` (init). The SDK never applies a page edit, never holds an element back and never loads the editor, whatever Joryio sends.

Added: site settings for page edits. Before asking for a page's edits the SDK reads `GET /v1/in-app/site-settings?sdkKey=` - a CORS-simple request, the key in the query string only, cached by the browser and the CDN for 60 s, the same answer for every visitor. Page edits switched off for the site, or no live page-edit campaign: no `/v1/in-app/page-edits` request on that page view, and edits applied from the session cache are undone. On a visitor's first view of a page (no selectors remembered for it yet) the SDK holds back the elements the site's live page edits change, from that answer - selectors only, never the body, inside the same 300 ms from the start of the page.

Added: UTM in page targeting. With `captureUTM` on, every in-app, placement and page-edit request's `context` carries `utm: { session, firstTouch }` - the five standard fields (`source`, `medium`, `campaign`, `term`, `content`) of this session's campaign and of this browser's first one, from what the SDK already recorded; never the query string. Page rules on the sources `utm_session` and `utm_first_touch` are matched on the device for overlays exactly as the server matches them.

Changed: the placements session cache and the page-edit stores are per workspace - their names carry a hash of the SDK key (`joryio_placements_v1_<hash>`, `jry_page_edits_<hash>`, `jry_page_edit_selectors_<hash>`, the scheme of the flags cache), so two workspaces on one site never read each other's answers. The unscoped stores of earlier builds are removed on load.

Web only: iOS, Android, React Native and Unity are not applicable - page edits, the page editor, page context and UTM landing data are browser concepts (no DOM, no URL, no query-string campaign landing in an app screen); the app equivalent is placements.

Added: `setLinkHandler((link) => boolean)` / `clearLinkHandler()` (work before `init()`, stubbed by the snippet): every link the SDK is about to open - an in-app message button or link, a placement button or HTML link, a card click - reaches your handler first as a `JoryioLink` (`url`, `source`: `in_app` / `placement` / `card`, `campaignId`, `placementKey`, `itemId`, `cardId`, `isAppDeepLink`, `openDefault()`), so a single-page app can route `https://shop.example/sale` with its own router instead of a new tab. Return true to take it over, false for the behaviour without a handler. Synchronous, so the click's user activation still holds when the SDK opens a tab. A root-relative in-app link reaches the handler resolved against the page. Refused schemes (`javascript:`, `data:`, ...) never reach it. `onDeepLink` options keep receiving app deep links, after the handler declines. `push` is part of the shared source values but never emitted on web: a push click is handled by the service worker. The same names and source values on all five SDKs.

Added: page edits and the visual editor (Joryio BACKLOG D444 Phase 4). Page-edit campaigns change elements of the page by CSS selector - `replace_text` (always set as text), `replace_image` and `replace_link` (absolute http(s) only), `hide`, `insert_placement` - fetched from `POST /v1/in-app/page-edits` for the current page, re-checked on the device (an untrusted edit is skipped whole), applied as elements appear (MutationObserver), undone and re-applied on a route change. Anti-flicker hides only the elements edited on this page last time, for at most `PAGE_EDIT_ANTI_FLICKER_MS` (300), never the body; static edits are remembered for the session, personalized ones never stored. Exposure `in_app.displayed` once an edit landed; a control visitor reports `in_app.control_viewed` once the element is on the page. A tab opened by the dashboard with `?joryio_editor=1` shows the point-and-click picker after the editor token (sent by `postMessage`, never in the URL) is verified with `POST /v1/in-app/editor/verify`; messages go only to the dashboard origin the token names. New capability `page_edits`.

Added: page context (Joryio BACKLOG D444 Phase 4, docs/PLACEMENTS_WEBSITE_LAYER.md) - campaigns can target pages by URL rules and page / dataLayer variables. Every in-app, placement and page-edit request reports the page URL (origin + path, never the query string or the fragment), the variables set with the new `setPageVariables(vars)`, and only the globals and dataLayer keys listed in the new `pageContext: { pageVariables, dataLayerVariables, dataLayerName }` option. Single-page-app route changes (`pushState`, `replaceState`, back) are new pages. New in-app trigger types `page_view`, `exit_intent`, `scroll_depth` (percent) and `time_on_page` (visible seconds). Overlays check their campaign's `pageTargeting` before every display and on every route change; the display-time re-check sends the page. A placement answer marked `pageScoped` is cached per page and asked again on a route change. New capability `page_context`. `setPageVariables` is stubbed by the snippet.

Added: content cards (Joryio BACKLOG D444 Phase 3, docs/PLACEMENTS_PLAN.md section 11) - a message center inside your site: a feed per person of cards (title, body, image, optional button / link, pinned, expiry) sent from Card campaigns and the journey step "Add card". `mountCardFeed(element, options?)` draws a plain feed into an element and returns a handle with `remove()` - image, title, body, button, a pinned marker, an unread dot and a dismiss x, drawn as text with the page's own font and colors (`.joryio-card-*` classes, no stylesheet of its own); `emptyText` ("No messages yet"), `pinnedLabel`, `dismissLabel` and `unreadLabel` can be replaced, and `onDeepLink` routes `myapp://` links. `getCards({ cursor? })` returns `{ cards, unreadCount, nextCursor, stateScope }` to draw yourself, `getUnreadCardCount()` reads the cache, `markCardViewed` / `markCardRead` / `markCardClicked` / `dismissCard` take a card or its id, `refreshCards()`, and `onCardsUpdated(cb)` returns a `JoryioSubscription` (`cancel()`, also callable). One `POST /v1/in-app/cards` (20 a page, `cards` capability, `etag` on the first page) cached in memory and `sessionStorage` for `CARD_FEED_TTL_SECONDS` (300) for the same visitor, at most once per `CARD_MIN_REFRESH_SECONDS` (30) with extra calls coalesced; `notModified`, `success: false` and HTTP 429 keep the cache; identify, reset, another tab switching the visitor and any consent change discard the cache and any answer still on its way. Reports are `POST /v1/in-app/track` `{ deliveryToken, action, sessionId }` with `viewed` / `read` / `clicked` / `dismissed`, each once per card, applied to the cache at once; the feed reports viewed then read once half a card was on screen for 1 s. An anonymous visitor (`stateScope: "device"`) keeps read / dismissed in `localStorage` (up to 500, cleared on identify, reset and wipeData). Without tracking consent nothing is requested or reported. Links follow the placement rule: http(s) in a new tab, an app deep link to `onDeepLink`, `javascript:` / `data:` / `file:` / `intent:` and the like never. The placement viewability measurement is now one shared helper used by placements and the feed. The nine methods are stubbed by the snippet. The same names and wire values on all five SDKs.

Added: placements (Joryio BACKLOG D444, docs/PLACEMENTS_PLAN.md) - named spots inside your pages that Joryio fills per visitor from placement campaigns and journey steps. `insertPlacement(key, element, options?)` draws one into an element and returns a handle with `remove()`; `<div data-joryio-placement="key"></div>` is filled automatically, including elements added later (`inApp.autoMountPlacements: false` turns that off). `getPlacements([keys])` hands you the data to draw yourself, with `item.markDisplayed()`, `item.markClicked(elementId?)`, `item.markDismissed()` and, for a held-out visitor, `placement.markDisplayed()`; `refreshPlacements(keys?)` and `onPlacementsUpdated(cb)` (returns a `JoryioSubscription`: `cancel()`, also callable). Every key asked for within 50 ms goes in one `POST /v1/in-app/placements` (up to 10 keys), answers are cached for the placement's `ttlSeconds` in memory and `sessionStorage` (for the same visitor only), and a key is fetched at most once per `PLACEMENT_MIN_REFRESH_SECONDS` (30); a 429 keeps the cache. An item counts as displayed once `PLACEMENT_VIEWABLE_FRACTION` (0.5) of it was in view for `IN_APP_DISPLAY_DWELL_MS` with the page visible; a held-out visitor's empty spot reports `in_app.control_viewed` the same way. Content is never swapped while the spot is on screen. HTML items use the overlay's sandboxed frame and nonce CSP and need `allowHtmlJsInAppMessages`. Without tracking consent the request names nobody (no user id, anonymous id or session; `trackingConsent` says why) and nothing is reported. New sync capabilities `placements` and `content.data`. The four methods are stubbed by the snippet. The same names and wire values on all five SDKs.

Fixed: content cards (D444, not released yet) - the device caches are per workspace, like the placements cache and the flags answer: the feed cache in `sessionStorage` and an anonymous visitor's read / dismissed state in `localStorage` now carry a hash of the SDK key (`joryio_cards_v1_<hash>`, `joryio_cards_device_v1_<hash>`), so two workspaces on one site never read each other's cards. The old origin-wide `joryio_cards_v1` and `joryio_cards_device_v1` entries are never read and are removed on start. No wire changes.

Fixed: placements (D444, not released yet) - the session cache is per workspace, like the flags answer below: its `sessionStorage` key now carries a hash of the SDK key, so two workspaces on one site never read each other's placements. The old origin-wide `joryio_placements_v1` entry is never read and is removed on start. No wire changes.

Fixed: feature flags (D446, not released yet) - the stored answer is per workspace. It was kept under one localStorage key for the whole origin, so two workspaces on one site that know a person by the same user id could read each other's flags. The key now carries a hash of the SDK key (the same one every other stored key uses); the old unscoped `jry_flags` is never read and is removed on start. No wire changes.

Fixed: feature flags (D446, not released yet). An exposure is logged once per visitor, flag and variant per session - after an account switch in the same session the next person's first read of a flag is their own exposure (it was skipped as already logged). An answer that was in flight when the visitor changed is still discarded, and the new visitor's flags are now fetched right after it (they waited for the next refresh). Found while building the iOS and Android flags.

Added: feature flags and remote config (Joryio BACKLOG D446). `getFlag(key, default)` and the typed `getBoolFlag`, `getStringFlag`, `getNumberFlag`, `getJsonFlag` return the value Joryio decided for this visitor, or your in-code default before the first answer, for a flag Joryio did not send, for a value of another type, or without tracking consent; they never wait for the network. `getAllFlags()`, `refreshFlags()` and `onFlagsUpdated(cb)` (returns a `JoryioSubscription`: `cancel()`, also callable). Nothing is fetched until the page uses flags; then one `POST /v1/flags/evaluate` returns every flag, kept in localStorage for the same visitor only and refreshed on start, when the page is shown again (at most once per `FLAGS_MIN_REFRESH_SECONDS`, 60), on identify / reset and on a consent change, with the `etag` so an unchanged answer is not sent again. The first read of a value in a session logs an exposure (`POST /v1/flags/exposures`, batched, once per flag and variant per session, skipped when the answer says `logExposure: false`). Browsers have no silent push, so `jry_sync: "flags"` applies to the native SDKs only. The eight methods are stubbed by the snippet. The same names and wire values on all five SDKs.

Added: every request names the SDK and its version - `X-Joryio-SDK: web` and `X-Joryio-SDK-Version: <version>` - on the event batches, the unload keepalive hand-off, in-app sync / resolve / track / form submit and every other API call (BACKLOG D427). Settings > Apps shows the oldest version each app ran in the last 7 days and when a newer SDK is out. The same wire names on all five SDKs; the web SDK has no bridge, so it never sends `X-Joryio-SDK-Wrapper`. The backend allows the headers in CORS on the public SDK routes. No personal data, nothing new stored on the device.

Added: recognise people who click your messages (Joryio BACKLOG D407). A tracked link from a Joryio message lands with `jr_t`, an opaque token Joryio signs and encrypts (no personal data in it, 7 days; added only to links to the workspace's own websites). On load the SDK removes `jr_t` from the address bar with `history.replaceState` - before the landing page is recorded, so the token is never bookmarked, shared or stored; `jr_cid` / `jr_jid` / utm_* stay - and, only while tracking is allowed (consent granted, not opted out, Do Not Track respected; held in memory while consent is `pending`, dropped on a denial or opt-out), sends it once to `POST /v1/identify-link` as `{ token, anonymousId }`. The server uses it only to attribute this visitor's events (Session Start, page views, conversions) to the recipient - it never identifies the browser as the contact. Not sent when a user is identified on the browser or a storefront identity token is held for this visitor - a link never overrides a stronger identity. New method `identifyFromLink(url)` for single-page apps and routers (also stubbed by the snippet). The same name and wire on all five SDKs.

Added: `resetTo(anonymousId)` - everything `reset()` does, then the anonymous id you pass instead of a random one, for an app that keeps its own visitor id (BACKLOG D366). The id must be 8 to 255 letters, digits, `.`, `_`, `:` or `-`, must not have the shape of a Joryio profile id (24 lowercase hex) and must not be the user id the SDK holds; a refused id is logged and the call is a plain `reset()` (a random id), so a logout is never skipped. The same name and rule on all five SDKs. No wire changes: the server sees an ordinary anonymous id. Like `reset()`, `resetTo` drops a click-link token the SDK has not sent yet (one held while consent is pending), so the link is never attributed to the next visitor on the browser. Also stubbed by the snippet.

Changed (BACKLOG D366, before any release of resetTo): it also refuses the anonymous id the SDK holds while a user is signed in - that id is tied to the signed-in person's profile, and adopting it would hand their in-app messages, events, form attribution and push subscription to the next person on a shared device (a random id is used instead). `resetTo` now resolves `true` (adopted) or `false` (refused, or the SDK is not initialized). The same on all five SDKs.

Changed (BACKLOG D366): `resetTo` also refuses the last 20 anonymous ids this device held for a signed-in user when a reset signed them out (stored locally, newest kept; `wipeData()` forgets them) - a random id is used and it answers `false`, the same message and cap on all five SDKs.

Added: the storefront identity token, for the Joryio store plugins. `storefrontIdentityToken` (init) / `setStorefrontIdentityToken(token)` set a token Joryio signs for a signed-in store customer's browser, bound to one anonymous id; `storefrontIdentityTokenProvider` (init) / `setStorefrontIdentityTokenProvider(fn)` supply a fresh one. Sent as `X-Joryio-Auth` on ANONYMOUS requests only, and only while the token's `vid` is the SDK's anonymous id and the request's; independent of `enableSdkAuthentication`. Not sent within 30 seconds of its expiry (the provider is asked instead). A `401 storefront_identity_error` refreshes it (`expired`) or drops it (any other reason) and retries once; an in-app form is sent once more the same way. `reset()` and `wipeData()` drop it. Both setters are stubbed by the snippet. Wire: the header is the existing `X-Joryio-Auth`; nothing changes for sites that do not set it.

Fixed: the `push_permission` profile attribute is reported only on a site that uses web push. It used to be written on every page load where it had changed - for a new visitor, always - even on a site that never turned web push on (for example the WordPress plugin with only in-app messages on): a `/v1/attributes` request per new visitor that said nothing anyone could act on and, for an anonymous visitor the SDK sent nothing else for, created a profile of its own.

Added: the `webPush` init option. `true`: reported on page load, as before. Unset (the default): reported once this browser has used web push - `push.subscribe()` was called or `push.prepare()` succeeded, on this or an earlier page view, or an earlier SDK version registered it - and from then on whenever it changes. `false`: never on page load; a `push.subscribe()` on the page still reports its answer. The WordPress, WooCommerce, Magento and PrestaShop plugins pass their Web push setting. Values and change detection unchanged (`granted`, `denied`, `not_determined`, `unavailable`, sent only when different from what the server acknowledged). No wire changes.

## 1.3.3 - 2026-11-03

Fixed: an in-app message counts as displayed only once someone could have seen it. It used to be counted - `in_app.displayed` reported and the campaign's frequency cap spent - the moment it was put on the page, so a message that appeared during a sign-in redirect, or just as someone clicked a logout link, used up the cap while it was visible for a flash at most. Now:

- a message appears only once the page has finished loading and gone idle, and never while the page is unloading (`beforeunload` / `pagehide`);
- it counts as displayed after it has been on screen for `IN_APP_DISPLAY_DWELL_MS` (1000 ms) with the tab visible. If the tab is hidden first the timer starts again when it is visible; if the page unloads first, nothing is reported, the frequency cap is untouched, and the message is eligible again on the next page;
- a click or a close by the person before then counts as seen: `displayed` is reported first, then the click or dismissal. Removal by the SDK or by your code (`dismissInAppMessage`, `reset()`) before then reports nothing.

Changed: `inApp.displayOptions.onDisplay` fires when the message counts as displayed, together with the `displayed` report, rather than when it is put on screen - the same timing as `onMessageDisplay` on iOS. `IN_APP_DISPLAY_DWELL_MS` is exported. No wire changes.

Fixed: the script-tag file (`joryio.min.js`, `joryio.umd.js`) is safe on a page with an AMD loader such as RequireJS (every Magento Luma store). Loaded by a plain `<script>`, the old UMD wrapper called an anonymous `define()`, which RequireJS attached to another module that was loading or reported as "Mismatched anonymous define() module" - and the SDK did not start. The SDK now always starts and sets `window.Joryio`; on an AMD page it defines an anonymous module only when RequireJS itself requested the file, and otherwise the named module `joryio-web-sdk`. Loading it with `require()` under any module id, as a CommonJS module or from npm (`import` / `require`) is unchanged.

## 1.3.2 - 2026-10-25

No change from the in-app hold added to the other four SDKs in this version (`holdInAppMessagesForHandler`): the web SDK always draws its own in-app messages and has no handler that takes drawing over after `init()` - its `inApp` hooks are passed in the init config, before the first sync - so the window that option closes does not exist here.

## 1.3.1 - 2026-10-24

Fixed: HTML modals and slide-ups are responsive. The message frame used to start narrow and take the width the content reported, so the author's media queries (for example `@media (max-width: 560px)`) fired even on a desktop screen. The frame is now given min(maxWidth, viewport width - 16px on each side) before the content loads (`maxWidth` comes from the "Max width" field in the dashboard; modal 600 and slide-up 400 when unset), re-fits when the window is resized, and only its height follows the content.

Fixed: the height is measured from the message body, so a message can shrink as well as grow (a form replaced by its thank-you line).

No API changes. Banner and fullscreen messages are unchanged.
